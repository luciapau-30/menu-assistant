# Piece of Mind — Database Design

## Purpose

This document defines the data model for Piece of Mind, including the entities, relationships, and storage decisions that support personalized food compatibility analysis.

The database is designed around the idea that food compatibility depends on multiple user-specific factors, including allergies, medical restrictions, dietary styles, nutrition goals, and personal preferences.

---

# Database Design Principles

## Scalability

User preferences and dietary requirements are stored using relational tables rather than fixed fields, allowing new categories to be added without redesigning the database.

---

## Separation of Data and Logic

The database stores information about users, food items, and analysis results. Compatibility calculations are handled by the Compatibility Engine rather than the database.

---

## Historical Data Preservation

Previous analyses and Compatibility Reports are stored to support user history, debugging, future improvements, and analytics.

---

# Core Entities

* Profile information


# User Profile Data

## Allergens

Represents ingredients that may cause allergic reactions.

Examples:

* Peanuts
* Tree nuts
* Dairy
* Eggs
* Fish
* Shellfish
* Soy
* Sesame
* Wheat

Relationship:

```text
User
 |
User_Allergen
 |
Allergen
```

A user may have multiple allergens.

# Analysis Data

## Analysis

Represents a user request to analyze food information.

Examples:

* Restaurant menu image
* Nutrition label image
* Ingredient list

Example fields:

```text
Analysis
--------
id
user_id
type
image_url
status
created_at
```

Possible types:

* MENU
* NUTRITION_LABEL
* INGREDIENT_LIST

Possible statuses:

* UPLOADED
* PROCESSING
* COMPLETED
* FAILED

---

## Extracted Menu Data

After image processing, structured information is stored rather than discarded.

Example:

```json
{
  "dish": "Chicken Bowl",
  "ingredients": [
    "chicken",
    "rice",
    "beans",
    "cheese"
  ]
}
```

Storing extracted data allows:

* Debugging OCR mistakes
* Re-running compatibility analysis
* Improving future models

---

# Important Database Decisions

## Multiple Compatibility Reports per Analysis

A single uploaded menu can contain many food items. Each item receives its own Compatibility Report.

---

## Store Extracted Data

Processed menu information is preserved after OCR and analysis to support debugging, future improvements, and reprocessing.

---

## Multiple User Goals

Users may select multiple nutrition goals because real-world objectives often overlap.

Example:

"Lose fat while maintaining muscle"

maps to:

* Weight Loss
* High Protein
